   ```bash
   npx supabase db push
   ```

## Performance baseline (Phase 0, 19 Nov 2026; plan in `docs/PLAN_SCALE_PORTAL_TASKS.md`)

sequential rounds of Supabase calls; each costs one round trip (~160 ms to Tokyo), plus the proxy's sign-in check.

| --- | --- | --- | --- |
| `/cockpit`, `/`, `/attendance`, `/sales` | 7-13 | 3 | ~640 ms |

Every page pays the shell (~4 calls: `rpc/me`, attendance session, timer, notifications). Latency, not query cost, dominates.

`EXPLAIN (ANALYZE, BUFFERS)` as a department member on 50k tasks / 100k notifications / 300k audit rows / 20k institutions:
- **`task_sel` is the one query-cost problem.** The `is_watching(id)` branch of the policy runs once per row the other branches
  reject: task list 93 ms (27.9k buffers), calendar window 81 ms (36k buffers), and it grows with the table. Fix in phase 4
  (rewrite the branch as a set lookup on `task_watcher`, not a per-row function call).
- `audit_log` has no index on `at` or `(table_name, row_id)`: seq scan, 12 ms at 300k rows, linear. Add both with retention.
- Institution search with a leading wildcard seq-scans 20k rows (13 ms); fine now, recheck with the trigram index at 100k.
- Everything else (my open tasks 1 ms, notifications 0.04 ms, unread count 1.6 ms, time entries 0.2 ms, institution
  list 0.1 ms, activities 0.2 ms) is index-backed. Indexes are not the bottleneck; round trips and the policy are.
